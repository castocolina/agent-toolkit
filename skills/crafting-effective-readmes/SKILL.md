# Crafting Effective READMEs

A README earns its place by getting its main reader to a first success that the repository actually supports. Most README defects are not prose problems: they are claims that drifted from the code, or commands that only work on the maintainer's machine.

## Workflow

1. **Pick the target file.** In a monorepo (root `package.json` `workspaces`, `pnpm-workspace.yaml`, Cargo `[workspace]`, `go.work`, several `pyproject.toml`), confirm whether the request is about the root README or one package's README before inferring anything: the signals for type, install method, and audience differ per package. When a request mixes update and audit, run the audit first and edit from its findings.
2. **Settle the reader and type.** The user's stated audience and purpose win over inferred signals. Then use evidence: target under `~/.config` or a dotfiles repo means Config; an employer-hosted remote means Internal. OSS needs both an OSI-approved license (check the SPDX id in LICENSE or the manifest, e.g. `MIT`, `Apache-2.0`, `GPL-3.0-only`) and a public intended audience. A public remote is not enough: proprietary or source-available terms (`BUSL-1.1`, `SSPL-1.0`, Elastic License, PolyForm, Commons Clause) and publication only to a private registry are not OSS, so state the actual terms. Take the contribution policy from repository evidence (CONTRIBUTING.md, CLA, PR template) or the user: a publicly intended source-available or commercial project takes the public layout (the OSS section layout and `templates/oss.md`, without calling the project OSS) with its real license and distribution terms, and invites contributions only if that evidence allows; use the Internal layout only for employer-hosted or access-restricted projects. A project meant for public release with no license chosen yet is OSS with a License placeholder. A missing remote is unknown, not Personal. If the type is still unresolved and would change the sections, ask one question; otherwise state the assumption in one line and continue.
3. **Decide the edit size.** Ask: will the reader's first success change? If yes (new install path, renamed command, new prerequisite), rewrite the quick-start and every section that repeats it. If no, add or edit only the section the change touches.
4. **Collect evidence before writing.** Prerequisites come from manifests (`engines.node`, `requires-python`, `rust-version`, `go` directive) and CI setup steps or test matrices, not from the local toolchain. Install commands come from the published identity: manifest `name`, `bin` / `[project.scripts]` / `[[bin]]`, and whether publishing is disabled. Read any generated-region markers now (see Gotchas).
5. **Write, validate, deliver.** Missing facts become visible placeholders (`<install command: not found in repo>`), never plausible inventions. Run Validation before delivering; then give the full README (creating), the changed sections or a diff (updating), or one line per stale claim citing the file and value that contradicts it (reviewing).

## Validation

1. Inspect the documented first-use commands before running any of them, and respect read-only and user-imposed constraints. Then run the path verbatim in an isolated clean environment: a fresh clone in a temp directory, a new virtualenv, or a container. Do not rely on an existing `node_modules`, `.env`, global installs, or shell aliases; those are what make maintainer-tested READMEs fail for new users. A command with external or destructive effects (publishing, deploying, writing outside the isolated directory, calling a paid or production service, `curl | sh`) runs only in an isolated environment and only with the user's authorization.
2. When a clean clone or container cannot be started, authorization is missing, or execution is otherwise not possible (no shell, no network, missing secrets), run the static manifest and CI check immediately instead: verify against manifests, source, and CI, label each claim `static` or `unverified`, never `executed`, and say so. Report each claim as `executed`, `static`, or `unverified`. Items the files cannot confirm (external links, hosted docs, CI badge status, registry availability) are labeled unverified in the output, never asserted as working or broken.

## Gotchas

- **Root commands are not package commands.** In a monorepo, `npm install` or `cargo build` at the root installs the workspace for contributors; a user needs the package's own published name (`npm install @scope/pkg`), which often differs from its directory name. A root `"private": true` only stops the workspace root from publishing; its packages publish independently. Markers like `"private": true`, Cargo `publish = false`, or a `Private :: Do Not Upload` classifier restrict publishing the current state; they do not prove the package is absent from a registry (an earlier release, or a private registry, may still serve it). To audit a registry install line, establish the intended registry (`publishConfig.registry`, `.npmrc`, pip `--index-url`, `.cargo/config.toml`) and the released version, then check availability against that registry when you have network access, passing it to each query: `npm view <name> versions --registry <url>`, `pip index versions <name> --index-url <url>`, and `cargo search <name> --registry <name>` (Cargo takes the name of a registry defined in its config, not a URL; omit the flag for crates.io). `cargo search` is a discovery aid that lists matching crates with their current version; it does not prove that an arbitrary documented version exists. For Cargo, check the exact documented version through the intended registry's version metadata: for crates.io, `https://crates.io/api/v1/crates/<name>/<version>`, or `cargo info <name>@<version>` where the installed Cargo has it (`cargo info` takes a `name@version` spec and a `--registry` option; Cargo book, https://doc.rust-lang.org/cargo/commands/cargo-info.html, checked 2026-11-15); if the exact version cannot be queried, mark that version unverified. A bare query hits the default registry (registry.npmjs.org, pypi.org, crates.io) and can give the wrong conclusion for a package published elsewhere. When the registry cannot be established or queried, or there is no network access, mark the line unverified. Options checked 2026-11-15 against https://docs.npmjs.com/cli/v10/using-npm/config#registry, https://pip.pypa.io/en/stable/cli/pip_index/ and https://doc.rust-lang.org/cargo/commands/cargo-search.html (pip and cargo were not installed here to read `--help`; npm was not run).
- **Install name, import name, and command name differ.** `pip install scikit-learn` imports `sklearn`; crate `my-tool` is `use my_tool`; an npm package's command comes from `bin`, not `name`. Check each one separately.
- **The default branch is not the release.** Registries show the README snapshot from the last published version, and GitHub shows the default branch. An example using an API added after the latest tag fails for everyone who installs the release; compare against the latest tag or changelog and mark unreleased features as such.
- **Generated regions are overwritten.** Text between markers such as `<!-- START doctoc ... -->`, `<!-- ALL-CONTRIBUTORS-LIST:START -->`, `<!-- BEGIN_TF_DOCS -->`, `<!-- toc -->`, or `<!-- cargo-rdme start -->` is rewritten by its tool on the next run, and a whole README built from `README.tpl` (cargo-readme) or `README.Rmd` is regenerated from that source. Edit the source (doc comments, config, template) or tell the user to rerun the tool; never hand-edit inside the region.
- **Registries render outside the repository.** PyPI does not resolve relative links or image paths, so they break on the project page; use absolute URLs, pinned to a tag, in any README that ships in a package. No official PyPI or Python Packaging User Guide page states this relative-link behavior (checked 2026-11-15 at https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/, which does not address it), so verify the current PyPI rendering before applying this rule. PyPI also renders Markdown only when the content type is `text/markdown`: with `readme = "README.md"` in `[project]` the build backend infers it from the extension (Python Packaging User Guide, https://packaging.python.org/en/latest/guides/making-a-pypi-friendly-readme/, checked 2026-11-15), whereas a `readme` table without `content-type` defaults to `text/x-rst` in setuptools (https://setuptools.pypa.io/en/latest/userguide/pyproject_config.html, checked 2026-11-15); a `setup.py` needs `long_description_content_type`. Verify the build backend before relying on any of this; otherwise PyPI treats the text as reStructuredText.
- **Anchor slugs differ by renderer.** GitHub and GitLab 17.0 and later lowercase, drop punctuation except `-` and `_`, keep repeated hyphens, and suffix duplicate headings `-1`, `-2`, so a table-of-contents link to `## A & B` is `#a--b` on both (GitHub docs, section links: https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#section-links, checked 2026-11-15: lowercase, punctuation removed, a counter suffix on duplicates; verify on the target renderer for any other host). Older self-managed GitLab instances may still collapse repeated hyphens (`#a-b`), so check links for the host and version the README is read on (GitLab docs, heading anchors: https://docs.gitlab.com/user/markdown/#heading-anchors, checked 2026-11-15).
- **HTML is sanitized differently.** GitHub and each registry strip different tags and attributes; HTML-only layout (aligned images, `<picture>` theme sources) degrades off GitHub. Keep the first-use path in plain Markdown.
- **Badges are claims.** A CI badge must name a workflow file that exists on the default branch; a registry badge needs a published package; a license badge must match LICENSE. In Internal READMEs, omit externally hosted badges by default: external badge services cannot read private repositories and are often blocked by corporate proxies, so they render broken for exactly that audience. A first-party or authenticated badge is fine once you have confirmed that audience can load it.

## References

Routing order: a Standard Readme request loads the specification (plus at most one of its examples) instead of the section checklist. Otherwise load the one guide that matches the task. Routine edits and audits load none. A project-type template loads on top of the checklist, only for the type chosen in Workflow step 2.

- `references/section-checklist.md`: when creating a README or restructuring one, to pick sections and type-specific content.
- `templates/oss.md`: only for the public layout: an OSS project, or a publicly intended source-available or commercial project (not called OSS: keep its actual license and distribution terms and derive the contribution policy from repository evidence, Workflow step 2). Badges are claims: keep only badges whose workflow file or published package exists, and take the license from LICENSE.
- `templates/personal.md`: only when the type is Personal.
- `templates/internal.md`: only when the type is Internal. The header carries Team and On-call; Dependencies lists upstream and downstream services; environment variables are a table of variable, description and where to get the value (never real values); troubleshooting is Symptom, Cause, Fix; externally hosted badges stay out.
- `templates/xdg-config.md`: only when the type is Config. Put `> Last reviewed: YYYY-MM-DD` under the title. Because Installation is omitted, it adds Why This Setup (goals, problems solved) and Dependencies (what must be installed for the config to work); Gotchas name files another tool writes and that must not be hand-edited.
- `references/standard-readme-spec.md`: only when the user asks for Standard Readme compliance. Then `references/standard-readme-example-minimal.md` for a small library, or `references/standard-readme-example-maximal.md` when badges, a table of contents, and optional sections are wanted.
- `references/art-of-readme.md`: only when the README buries what the project does under install or reference detail and needs reordering for the reader. Do NOT load it (536 lines) for other tasks.
- `references/make-a-readme.md`: only when the user wants the purpose of a common section explained.

For prose quality beyond README structure, use the `writing-clearly-and-concisely` skill.
