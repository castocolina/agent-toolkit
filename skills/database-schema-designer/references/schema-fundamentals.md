# Schema design fundamentals

Background the user may ask for by name: normal forms, denormalization, key choice, foreign-key actions, junction tables, MongoDB index syntax, reading a MySQL EXPLAIN and a basic do and avoid list. It restates textbook rules in this skill's terms. Where SKILL.md has an engine-specific gotcha, the gotcha wins; this file points to it instead of repeating it. Examples are PostgreSQL unless a line says otherwise.

## Core principles

| Principle | Why | In practice |
|-----------|-----|-------------|
| Model the domain | The UI changes, the domain does not | Entity names reflect business concepts, not screens |
| Integrity first | Corruption is costly to fix | Constraints in the database, not only in application code |
| Optimize for the access pattern | One layout cannot serve both OLTP and OLAP | OLTP: normalized. OLAP or reporting: denormalized |
| Plan for scale | Retrofitting is painful | An index per named query, and the partitioned-tables gotcha when retention drops whole ranges |

## Normalization

| Form | Rule | Violation example |
|------|------|-------------------|
| 1NF | Atomic values, no repeating groups | `product_ids = '1,2,3'` |
| 2NF | 1NF and no partial dependency on part of a composite key | `customer_name` in `order_items` |
| 3NF | 2NF and no transitive dependency | `country` derived from `postal_code` |

Third normal form, with the dependency moved to its own table:

```sql
-- Violates 3NF: country depends on postal_code, not on the customer.
CREATE TABLE customers (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  postal_code VARCHAR(10),
  country VARCHAR(50)
);

-- 3NF: the dependency has its own table.
CREATE TABLE postal_codes (
  code VARCHAR(10) PRIMARY KEY,
  country VARCHAR(50) NOT NULL
);
CREATE TABLE customers (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  postal_code VARCHAR(10) REFERENCES postal_codes (code)
);
```

Normalize to 3NF first, then denormalize selectively and record why. Typical reasons:

| Scenario | Denormalization strategy |
|----------|--------------------------|
| Read-heavy reporting | Pre-calculated aggregates |
| Expensive joins | Cached derived columns |
| Analytics dashboards | Materialized views |

```sql
-- Denormalized on purpose: total_amount and item_count are derived from order_items.
-- Whatever writes order_items (a trigger or the service) must keep them in step.
CREATE TABLE orders (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id BIGINT NOT NULL REFERENCES customers (id),
  total_amount NUMERIC(12, 2) NOT NULL,
  item_count INTEGER NOT NULL
);
```

The bounded-slice-plus-counter pattern in the MongoDB 16 MiB gotcha in SKILL.md is the document-store form of the same trade.

## Keys

- Every table has a primary key. A surrogate key is the default: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (the migration template uses it; MySQL spells it `AUTO_INCREMENT`).
- Use a UUID when keys are generated by several systems. Prefer the engine's native UUID type over `CHAR(36)`, and read the target engine's docs for the generator function and its version.
- A junction table takes a composite key: `PRIMARY KEY (student_id, course_id)`.
- Do not use meaningful values such as an email or username as the primary key. They change and leak. Keep them as `UNIQUE` columns.
- The primary key is indexed automatically. Verify it anyway when reviewing.

## Foreign-key actions

```sql
FOREIGN KEY (customer_id) REFERENCES customers (id)
  ON DELETE CASCADE      -- delete the children with the parent
  ON DELETE RESTRICT     -- refuse the delete while children exist
  ON DELETE SET NULL     -- null the reference when the parent goes
  ON UPDATE CASCADE      -- rewrite children when the parent key changes
```

The `ON DELETE` lines are alternatives: a real key carries one of them.

| Action | Use when |
|--------|----------|
| `CASCADE` | The child has no meaning without the parent (`order_items`). Check the fan-out first: one delete can remove millions of rows in one transaction (checklist check 2). |
| `RESTRICT` | An important reference where a delete is more likely an accident |
| `SET NULL` | An optional relationship. On a composite tenant FK use the column list or `RESTRICT` (gotcha: composite SET NULL). |

`ON UPDATE CASCADE` matters only when parent key values can change; with a surrogate key they do not, so it is not a default. Every FK must also be indexed or consciously skipped per the FK indexing gotcha, which replaces the old "index every foreign key" rule.

## Many-to-many

```sql
CREATE TABLE enrollments (
  student_id BIGINT NOT NULL REFERENCES students (id) ON DELETE CASCADE,
  course_id BIGINT NOT NULL REFERENCES courses (id) ON DELETE CASCADE,
  enrolled_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (student_id, course_id)
);
-- The primary key serves lookups by student_id. If courses are listed with their
-- students, add an index starting with course_id (gotcha: FK indexing).
CREATE INDEX idx_enrollments_course ON enrollments (course_id);
```

## Numeric types

| Type | Use |
|------|-----|
| Small integer types (MySQL `TINYINT`, PostgreSQL has none) | Status codes and ages |
| `SMALLINT` | Quantities |
| `INTEGER` | IDs and counts |
| `BIGINT` | Large IDs, epoch timestamps |
| `DECIMAL(p,s)` / `NUMERIC(p,s)` | Exact values, so money |
| `FLOAT` / `DOUBLE PRECISION` | Approximate, scientific data only |

The integer ranges differ per engine: read the target engine's integer-types page (MySQL: https://dev.mysql.com/doc/refman/8.4/en/integer-types.html) before sizing a column, and size to the real maximum plus headroom.

```sql
price NUMERIC(10, 2)   -- exact; holds up to 99,999,999.99
price DOUBLE PRECISION -- never for money: rounding errors
```

SKILL.md "Money" has the full rule: SQLite integer minor units, MongoDB `Decimal128`, and a currency column.

## MongoDB index syntax

```javascript
// Unique single field
db.users.createIndex({ email: 1 }, { unique: true });

// Compound: tenantId first (SKILL.md MongoDB gotcha), then the equality field, then the sort
db.orders.createIndex({ tenantId: 1, customer_id: 1, created_at: -1 });

// Text search
db.articles.createIndex({ title: "text", content: "text" });

// Geospatial
db.stores.createIndex({ location: "2dsphere" });
```

Single-tenant data drops `tenantId`. Read the createIndex page of the manual for the target server's options.

## Reading a MySQL EXPLAIN

```sql
EXPLAIN SELECT id, status, total FROM orders
WHERE customer_id = 123 AND status = 'pending';
```

| Look for | Meaning |
|----------|---------|
| `type: ALL` | Full table scan (bad on a large table) |
| `type: ref` | An index is used (good) |
| `key: NULL` | No index chosen |
| `rows` high | Many rows examined |

Column meanings vary by version: https://dev.mysql.com/doc/refman/8.4/en/explain-output.html. Plain `EXPLAIN` plans without running the statement; see the EXPLAIN gotcha in SKILL.md before using `EXPLAIN ANALYZE` on a write.

## The N+1 query problem

An application pattern, not a schema change: one query for the list, then one query per row.

```python
# N+1: one query per order
orders = db.query("SELECT id, customer_id FROM orders")
for order in orders:
    customer = db.query("SELECT name FROM customers WHERE id = %s", (order.customer_id,))

# One join
results = db.query("""
    SELECT orders.id, customers.name
    FROM orders
    JOIN customers ON orders.customer_id = customers.id
""")
```

Always pass values as bind parameters; never build SQL with f-strings. The join needs an index on `orders.customer_id` per the FK indexing gotcha. Tuning beyond this is outside the skill.

## Do and avoid

Do:

- Start from domain modeling, not UI requirements.
- Normalize to 3NF first, then denormalize selectively.
- Use an exact type for money, never `FLOAT` (SKILL.md "Money").
- Define foreign keys for every relationship, on an engine and connection that enforce them (gotchas: MyISAM, SQLite).
- Size `VARCHAR` columns for the real data.
- Store dates in date and time types, with the right one per case (SKILL.md "Time types").
- Test migrations on staging with production-like data (`references/migrations.md`, Review before shipping).

Avoid:

| Anti-pattern | Problem | Instead |
|--------------|---------|---------|
| `VARCHAR(255)` everywhere | Wastes space, hides intent | Size per field |
| `FLOAT` for money | Rounding errors | `NUMERIC(10,2)` or integer minor units |
| Missing FK constraints | Orphaned data | Define the foreign key |
| Dates stored as strings | Cannot compare or sort | `DATE` or `timestamptz` |
| `SELECT *` in application queries | Fetches unneeded data | Explicit column lists |
| `NOT NULL` without a default on a populated column | Breaks existing rows | Add nullable, backfill, then constrain (`references/migrations.md`, Add NOT NULL) |

Two old absolutes are deliberately not restored: "index every foreign key" is replaced by the per-engine FK indexing gotcha, and "always write a DOWN migration" by the down-migration data-loss warning in `references/migrations.md`.

## Basic-design checklist for a sketch

Keys and relationships:

- [ ] Every table has a primary key; its type is chosen (identity or UUID), not an email or username
- [ ] Every relationship has an FK, and each FK has a deliberate `ON DELETE`
- [ ] Each FK is indexed or its skip is explained (FK indexing gotcha)

Types and constraints:

- [ ] Column types fit the data: exact type for money, integers for counts, `VARCHAR` sized for the data
- [ ] Instants, civil dates and local times follow the Time types gotcha; timestamps in UTC means `timestamptz`, not plain `timestamp`
- [ ] `NOT NULL` on required fields, `UNIQUE` where the domain needs it, `CHECK` for validation
- [ ] `created_at` and `updated_at` where the table needs history

Normalization and indexes:

- [ ] No repeating groups (1NF), no partial dependencies on a composite key (2NF), no transitive dependencies (3NF)
- [ ] Any denormalization has its reason written down
- [ ] Each index names a query: WHERE columns, ORDER BY columns, or an FK path. Composite order is equality columns first, then range or sort (checklist check 6)

Delivery:

- [ ] Migration scripts have a recovery path, and a down script that drops data says so
- [ ] Tested on staging with production-like volume

For a review of an existing schema, use `references/schema-design-checklist.md` instead.
