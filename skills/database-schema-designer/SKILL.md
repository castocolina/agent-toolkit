# Database Schema Designer

## Defaults when context is missing

For these four routine design defaults, do not stop to ask. Answer with a concrete design, and state all four as `Assumption:` lines every time, scale included: either the default or the value the prompt gave.

- PostgreSQL 15 or later, unless an engine is named; label any dialect-specific syntax. 15 is the floor for `ON DELETE SET NULL (cols)` and `UNIQUE NULLS NOT DISTINCT` (both added in 15.0, https://www.postgresql.org/docs/release/15.0/, checked 2026-11-07); for the live supported versions read https://www.postgresql.org/support/versioning/ (checked 2026-11-07).
- A new schema with no production data, unless the prompt mentions a live app, existing rows or a deploy.
- Single tenant, unless organizations, accounts, workspaces or tenants are named.
- OLTP on one primary, up to tens of millions of rows per table.

For another named engine (SQL Server, Oracle, DynamoDB), apply the workflow questions and the engine-neutral gotchas (tenant references, soft-delete uniqueness, money, column meaning). State in an `Assumption:` line that its lock and online-DDL behavior is unverified by this skill.

Facts about existing data are not defaults. Examples: the value that replaces existing NULLs, the time zone that old `timestamp` rows were written in, or which tenant owns a mismatched row. When a live change depends on one of these, do not invent it. Give the diagnostic SQL that sizes the problem (`SELECT count(*) ... WHERE phone IS NULL`) and the staged plan. Write each mutating statement with a named placeholder such as `:owner_confirmed_value` or `AT TIME ZONE :source_zone`, and mark it as blocked until the owner confirms.

In a tenant model, `users` is its own table; a membership table such as `organization_users` does not replace it.

## Workflow

1. **Before designing, answer four questions and act on each answer.**
   - Live data? If any table already holds production data, on a relational engine read `references/migrations.md` before writing DDL; on MongoDB follow the five-step in-place shape change in the "MongoDB has no foreign keys" gotcha and write no SQL DDL.
   - Tenant noun? If yes, on a relational engine every tenant-owned child gets the composite-FK gotcha; on MongoDB follow the tenancy rules in the "MongoDB has no foreign keys" gotcha.
   - Atomic writes? The writes that must commit together set the table or document boundaries. In MongoDB, embed a child only when it is read with its parent, bounded in size, owned by that parent alone, and updated atomically with it. Reference it when it is shared across parents, grows without bound (see the 16 MiB gotcha), is queried on its own, or is updated independently at a high rate.
   - Hot reads? Each index you add must name one.
2. **Indexes.** Each index names the hot read or FK path it serves, and skipping an index is a valid, documented decision. Verify with the engine's plan command on production-like row counts: `EXPLAIN (ANALYZE, BUFFERS)` on PostgreSQL and `EXPLAIN ANALYZE` on MySQL (confirm the target server version supports it) for reads (`SELECT`), `EXPLAIN QUERY PLAN` on SQLite, `explain("executionStats")` on MongoDB. Read the engine's own EXPLAIN page before quoting options, such as https://www.postgresql.org/docs/current/sql-explain.html and https://dev.mysql.com/doc/refman/8.4/en/explain.html. For writes, see the EXPLAIN gotcha.
3. **Migrations (relational only).** Before writing one, classify each statement: does it rewrite the table, which lock does it take, and must it run outside a transaction (`CREATE INDEX CONCURRENTLY`) or apart from the step before it (`NOT VALID`, then `VALIDATE`)? Put each phase in its own migration file. On PostgreSQL and MySQL, start each file from `assets/templates/migration-template.sql`. On SQLite, skip the template and write the rebuild in the order under "SQLite table rebuild" in `references/migrations.md`, with the `PRAGMA` outside the transaction.
4. **Check before answering.** For a sketch, confirm that every named entity has a table, every FK has a deliberate `ON DELETE`, money and instant columns use the gotcha types, and each index names its query. For a sketch the user wants a plain basic-design checklist for, read `references/schema-fundamentals.md`. When auditing an existing schema or finalizing a design, read `references/schema-design-checklist.md` instead and report in its format: every finding carries its own complete corrected DDL with every statement written in full, never "same as F7" or a "then: ..." shorthand list, every alternative path written in full too, and any statement it depends on from another finding (such as an index) repeated, and a finding that is not a schema change (a cleanup or retention job, a backfill) carries the exact SQL statement to run. On MongoDB, give the exact `mongosh` command or the application change instead.

## Gotchas

- **Cross-tenant references pass a plain FK.** `tasks.project_id REFERENCES projects(id)` accepts a project from another organization. Carry `organization_id` into each child and use composite FKs, `FOREIGN KEY (organization_id, project_id) REFERENCES projects (organization_id, id)`, backed by `UNIQUE (organization_id, id)` on the parent (an FK target must be a PK or unique key). For a task's assignee, branch on who owns the identity. If each user belongs to exactly one organization, reference `users (organization_id, id)`. If identities are shared across organizations, keep `users` plus `organization_users (organization_id, user_id)` and point the FK at `organization_users (organization_id, user_id)`. Application filters do not count, and PostgreSQL FK checks bypass row-level security.
- **`ON DELETE SET NULL` on a composite tenant FK also nulls the tenant column**, which fails or orphans the row. On PostgreSQL 15+, write `ON DELETE SET NULL (assignee_id)` to null only the reference. MySQL, SQLite and PostgreSQL before 15 lack the column list: use `ON DELETE RESTRICT` on the composite FK, and in the same transaction as the delete run `UPDATE tasks SET assignee_id = NULL WHERE organization_id = ? AND assignee_id = ?` first.
- **Foreign keys are indexed differently per engine.** PostgreSQL does not index the referencing columns, so each parent `DELETE` or key `UPDATE` scans the child table. Index them when parents are deleted or joined from the parent side, unless an existing index starts with those columns. MySQL InnoDB creates the index itself if none exists, so do not add a duplicate.
- **MySQL ignores foreign keys on MyISAM.** For engines without FK support, MySQL parses and ignores the specification (https://dev.mysql.com/doc/refman/8.4/en/ansi-diff-foreign-keys.html, checked 2026-11-07); run `SHOW WARNINGS` on your server to see whether it also warns. Check `ENGINE=InnoDB` before relying on one.
- **SQLite enforces foreign keys only on connections that ran `PRAGMA foreign_keys = ON`.** It is off by default, it must be set per connection, and inside a transaction it is silently ignored. SQLite `ALTER TABLE` supports only RENAME, RENAME COLUMN, ADD COLUMN, DROP COLUMN and, from 3.53, `ALTER COLUMN ... SET/DROP NOT NULL` and `ADD CHECK` (https://www.sqlite.org/releaselog/3_53_0.html, checked 2026-11-07; read https://www.sqlite.org/lang_altertable.html for the exact syntax on the target version). A type change, UNIQUE, PRIMARY KEY or FOREIGN KEY needs the 12-step rebuild in `references/migrations.md`.
- **Polymorphic parents** (a comment on an article or a photo): a `commentable_type`/`commentable_id` pair cannot carry an FK, so orphans go unnoticed. Use one nullable FK per parent type plus `CHECK (num_nonnulls(article_id, photo_id) = 1)` on PostgreSQL (read `num_nonnulls` at https://www.postgresql.org/docs/current/functions-comparison.html); on MySQL and SQLite write it as the table constraint `CHECK ((article_id IS NOT NULL) + (photo_id IS NOT NULL) = 1)`. MySQL prohibits `ON UPDATE`/`ON DELETE` actions on columns used in a CHECK (https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html, checked 2026-11-07), so those FKs keep the default action there. Or use a shared supertype table the FK can target.
- **Partitioned tables** (PostgreSQL time series): every PRIMARY KEY or UNIQUE must include the partition key, such as `PRIMARY KEY (device_id, ts, id)`, so a plain `id` primary key is rejected. Partition by time when retention should drop whole ranges (detach or drop a partition instead of a mass `DELETE`), or when the table outgrows the default scale.
- **Unique keys accept many NULLs** in PostgreSQL, MySQL and SQLite. If a missing value must also be unique, use PostgreSQL 15+ `UNIQUE NULLS NOT DISTINCT` or make the column `NOT NULL`.
- **Soft delete breaks plain uniqueness**, because deleted rows still collide with new ones. In PostgreSQL use `CREATE UNIQUE INDEX ... (email) WHERE deleted_at IS NULL`. MySQL has no partial indexes: add a generated column `active_email AS (IF(deleted_at IS NULL, email, NULL))` with a unique key on it, which works because NULLs do not collide (read https://dev.mysql.com/doc/refman/8.4/en/create-table-generated-columns.html for the target version). On a live table, add the new unique key before dropping the old one, so active rows are never left without uniqueness.
- **Time types.** For instants (created_at, paid_at), PostgreSQL `timestamptz` stores UTC and converts on output by the session `TimeZone`. Plain `timestamp` silently drops the offset of `'2026-01-01 10:00+02'`, and for instants that is wrong. For civil dates (birthday, due date) use `DATE`. For future local events (an appointment at 09:00 in Madrid), store the local `timestamp` plus an IANA zone name such as `Europe/Madrid`, because zone rules can change before the event. In MySQL, `TIMESTAMP` converts through the session `time_zone` but ends at 2038-01-19; `DATETIME` has no conversion, so pin the session `time_zone = '+00:00'` and store UTC.
- **Money.** On PostgreSQL and MySQL use fixed-scale `NUMERIC`/`DECIMAL`. SQLite's `DECIMAL(10,2)` gets NUMERIC affinity, ignores the precision and stores `0.1` as REAL, so use `INTEGER` minor units with a documented scale and a `CHECK` range. On MongoDB use `Decimal128`. Store a currency column, or document the single currency.
- **MongoDB has no foreign keys, so tenancy and references live in the service layer.** Store `tenantId` on every document and inside every reference, put it first in each query filter and compound index, and check that a referenced document has the same `tenantId` in the same service call that does authorization. A `$jsonSchema` validator can require `tenantId` and field types, but it cannot check that a reference exists or belongs to the tenant. Tightening a validator with `collMod` does not re-check existing documents, so find stragglers with `db.c.countDocuments({ $nor: [ { $jsonSchema: <schema> } ] })` (see https://www.mongodb.com/docs/manual/core/schema-validation/use-json-schema-query-conditions/). Shape changes happen in place, in this order: (1) deploy readers that accept both shapes everywhere; (2) deploy writers of the new shape and drain every old writer and worker, which would otherwise keep creating legacy documents; (3) backfill in idempotent batches whose filter matches only the legacy shape, so a rerun is a no-op; (4) reconcile until the legacy filter counts zero; (5) only then tighten the validator with `collMod`. When moving data to another collection, capture concurrent writes with dual writes or a change-stream reconciliation before cutting readers over. Do not write SQL-style DDL migrations for MongoDB.
- **MongoDB documents stop at 16 MiB** (https://www.mongodb.com/docs/manual/reference/limits/, checked 2026-11-07), and an embedded array that grows with activity (comments, followers) reaches that limit. Reference such data; embed at most a bounded slice (the latest N via `$push` with `$slice`) plus a counter.
- **Never change what an existing column means in place.** This covers values whose format application code depends on: enum or status codes, units (dollars to cents), ID or token formats, and the hash algorithm in `api_token_hash`. During a rolling deploy, old and new app versions read and write the same column, so an in-place change silently corrupts rows. Add a new column or a version marker, and follow expand-contract in `references/migrations.md`.
- **`EXPLAIN ANALYZE` executes the statement**, on PostgreSQL and on MySQL alike. For `INSERT`, `UPDATE` and `DELETE`, default to plain `EXPLAIN`, which plans without running. Use `EXPLAIN ANALYZE` on writes only against disposable production-like data, or inside `BEGIN; ... ROLLBACK;`. The rollback does not undo sequence or `AUTO_INCREMENT` increments, MyISAM changes, or external calls from triggers. On MySQL, any DDL inside the wrapper commits implicitly and ends it. MySQL 8.4 measures only `SELECT`, `TABLE` and multi-table `UPDATE`/`DELETE` (https://dev.mysql.com/doc/refman/8.4/en/explain.html, checked 2026-11-07); for a single-table `UPDATE` or `DELETE` it reports that the statement is not executable by the iterator executor, so run it on your server to see the exact text. Plans from a near-empty dev table differ from production plans, so test on production-like row counts with fresh statistics.
