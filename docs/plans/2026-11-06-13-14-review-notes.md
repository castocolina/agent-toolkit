## Plan 14, content recovery

- **[native Opus] The queue does not say whether batches mix modes, yet the PR count depends on it** — Location: Task 1 `recovery queue` (order key; "No batch holds more than 3 artifacts"); PR layout ("21 batches, 18 `full`, 2 `facts-only` and 1 `report-only`"). Required: the queue interface states whether batches are chunked per mode or across mode boundaries, and Task 1 Step 1 tests it. Why: chunking the ordered list in threes gives 18 + [3 facts-only] + [1 facts-only, 2 report-only] = 20 batches, not 21. That changes the last-PR arithmetic and creates mixed `facts-only`/`report-only` batches the close rules do not describe.
- **[native Opus] `RUNNER` is written as the command text rather than its output** — Location: Task 3 Step 7 ("`RUNNER` = `python3 scripts/audit/audit.py pi-cmd runner --model <referee lane>`"); Task 1 `presence --runner CMD` ("a referee lane through `pi-cmd`"). Required: `RUNNER="$(python3 scripts/audit/audit.py pi-cmd runner --model <lane>)"`, as plans 8 and 12 write it. Why: `pi-cmd` prints a shell-joined command (`audit.py` main, `pi-cmd` branch). Passing the literal string as `--runner` makes every eval and presence call fail, and those failures would be read as fix-round inputs.
- **[native Opus] `BASE` values are not persisted, and Task 4 needs one after compaction** — Location: Task 3 opening ("note `BASE`"); Task 4 Step 1 (`git diff <first batch's BASE> -- docs/audit/upstream-sources.json`); Step 8 ("compact to 3-6 commits"). Required: a durable reference for the sources-found column, either a recorded ref in a committed file or a ref derivable after compaction (e.g. the Task 2 queue commit on the final branch). Why: the first batch's `BASE` is only noted in-session, and the Step 8 compaction of PR 1 rewrites that SHA. A later session (handoff) cannot reproduce it.
- **[native Opus] Nothing says when the next PR's branch is created** — Location: PR layout; Task 3 Step 8. Required: a step after each Step 8 creates `fix/<yy-mm-dd>-content-recovery-<n+1>` from the pushed head (and its worktree `<wt>`) before the next batch opens, as plan 8 Step 8 does ("continue with the next batch on a new branch"). Why: a zero-context executor would keep committing batches 5-8 onto the already-open PR 1 branch.
- **[native Opus] The PR-boundary form has no rule for an unattended run** — Location: Task 3 Step 3 ("go to the user in one AskUserQuestion form before the push"; "An answer that arrives after the PR is open …"). Required: state whether the push waits for answers, or proceeds with pending rows left at their safe defaults when no answer comes. Why: "before the push" and "after the PR is open" give two readings. The run is unattended, so the blocking reading stalls the plan, which goes against "never blocks a batch".
- **[native Opus] Remote presence-judge consent has no stated location or fallback** — Location: Global Constraints, Remote judges ("only under the user's recorded consent for that backend"). Required: name where consent is recorded and checked, and the fallback runner when none exists (e.g. a referee lane or a local backend).
