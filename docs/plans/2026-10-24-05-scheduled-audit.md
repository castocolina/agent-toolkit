# Plan 5 — Scheduled Audit Workflow

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every ~15 days GitHub Actions refreshes the Agent Skills spec and the rubric, judges the skills that changed with several Copilot models, merges the verdicts, re-checks upstream sources, and — only when something needs updating — opens a fix PR whose merge mode is a repo knob. **Amendment A (below) supersedes the merge-mode knob and the Copilot-bot review gate: the Copilot agents use jev (TypeSafe System One) through the official `typesafe-ai` skill for their typed judgments, scripts verify what they did, and a review job with its own knobs decides what happens to the PR.**

**Architecture:** One scheduled workflow with LLM-free gating (`detect`) in front of Copilot jobs, all reusing `scripts/audit/audit.py` and the skills from plans 2-4; a second workflow merges `agent` PRs directly, only for a head with a Copilot review of that exact SHA and green required checks. Stale upstream sources produce an issue, never a fix. State advances only after a durable outcome.

**Tech Stack:** GitHub Actions, GitHub Copilot CLI (`copilot -p`), `gh`, `uv`, `actionlint`.

**Spec:** [Roadmap](2026-10-24-00-roadmap.md) — Decisions 4, 5, 6, 8, 9, 11, 18; planner calls C6, C7, C9; Global Constraints apply.

Branch: `feat/<yy-mm-dd>-scheduled-skill-audit`. Depends on plans 2, 3 and 4.

## Review Focus

1. Scheduled run with no spec change, no skill change and no new stale upstream source → zero Copilot calls. Pinned in Task 2.
2. A run that judges only the changed skills → merge is scoped to them and can complete. Pinned in Task 3 job 4.
3. A run fails after research, or `detect` fails (`audit.py upstreams` exits 1 or 2) → `AUDIT_LAST_STATE` untouched, the next run retries. Pinned in Task 3 jobs 1 and 8 and Step 8.
4. An audit PR is closed without merging after a spec change → the next run still sees the spec as changed (comparison is against the committed references, not stored state). Pinned in Task 2.
5. Required status checks are enabled for `auto`/`agent` → the existing direct-push bots (`auto-bump`, `sync-*`) keep working. Pinned in Task 1 Step 5.
6. Upstream adds, removes or renames a skill-creation page, or renames/removes a heading the rubric cites → detected (`structure_changed`, or `rubric-check` failing on a broken `source` anchor), treated as a spec change, and the audit PR updates the research skill (file list, fixtures, tests) and the judge (rubric sources, criteria, eval file lists); never silently ignored. Pinned in Task 2a and Task 3 jobs 1 and 2 (every repair travels in `repairs.patch`).
7. An interrupted refresh (references committed, rubric not updated) → `rubric_stale` counts as a spec change, so the next run refreshes the rubric. Pinned in Task 2 (`--spec-changed` definition) and Task 3 job 1.
8. A research leg fails or a configured judge is missing → `merge` exits 2 (`--min-judges` = number of configured models) and the state is untouched. Pinned in Task 3 job 4 and Step 8(a).
9. The eval harness fails (`run-evals` exit 2) → no decision, no PR, no state advance; plain quality failures (exit 1) are only evidence. Pinned in Task 3 job 3 (`evals`) and Step 8(c).
10. A PR created in `manual` or `auto` mode (dispatch override included) is never merged by the review gate. Pinned in Task 3 job 6 and Step 9. *(Superseded by Amendment A, item 22.)*
11. `update=true` but `apply` fails, or `update=false` (no PR) → state advances only on a durable outcome (a PR for `true`, a validated "no update" for `false`), and `merge-knob` never runs without a PR. Pinned in Task 3 jobs 5-8 and Steps 6, 8(d). *(Still holds; the merge-mode wording is superseded by Amendment A.)*
12. A commit lands on an `agent` PR after the Copilot review, or while its checks are pending → never merged unreviewed: the gate merges directly, only for a head with a qualifying review of that exact SHA and green required checks, and `--match-head-commit` makes GitHub refuse a moved head; persistent auto-merge is never enabled in `agent` mode. Pinned in Task 3 job 6 and Step 9. *(Superseded by Amendment A, item 22.)*
13. A leftover remote branch from a closed-unmerged audit PR → the next run uses a suffixed name instead of failing. Pinned in Task 2 and Task 3 job 5.
14. A dispatch overlaps a scheduled run → the runs queue and never interleave (one audit PR, one state write). Pinned in Task 3 (workflow `concurrency`) and Step 8(e).
15. An inspiration source gets newer while skills and spec are unchanged → one `audit-upstream` issue with a recommendation, no fixer, state advances only its upstream part, nothing applied without the user's approval (Decision 11). Pinned in Task 2 and Task 3 jobs 1 and 7, Step 8(f).
16. The daily `sync-*` commits to `gepetto`/`datadog-cli` → never a reason to run, never judged. Pinned in Task 2.
17. Upstream lists a new in-scope page → its content (at the resolved upstream SHA) is on disk for the editing-capable repair job, which cannot fetch anything itself; the job fails rather than guess when a listed new page is missing. Pinned in Task 2a (`--pages-dir`) and Task 3 jobs 1-2, Step 8(g).
18. A shallow checkout in `detect` → `audit.py upstreams` would report the checkout commit as every skill's last change and find no merge base, hiding stale sources while the state advances. `detect` checks out with `fetch-depth: 0` and fails on a shallow clone. Pinned in Task 3 job 1, Step 8(h).
19. The repo's default workflow-token permission is read-only → every job still works, because each workflow declares its own least-privilege `permissions:` (`detect`'s open-PR check needs `pull-requests: read`). Pinned in Task 1 Step 5, Task 3 "Permissions", Step 6.

### Task 2a: Upstream structure drift (roadmap Decision 18)

Today `fetch-spec.sh` tracks a hardcoded list of 7 upstream files (plan 2 Task 1): a page upstream adds is never noticed, a removed or renamed page only fails the fetch (exit 1) with no recovery path, and a renamed heading silently breaks the rubric's `source` anchors (`rubric-check` does not verify them). The agentskills.io navigation is `docs/docs.json` in `agentskills/agentskills`; this task makes the fetcher and the checker detect structural drift so the audit PR can update the research skill and the judge.

**Files:** Modify `skills/agentskills-research/scripts/fetch-spec.sh`, `tests/skills/agentskills-research/test-fetch-spec.sh`, its fixtures in `tests/skills/agentskills-research/fixtures/` (add `docs/docs.json` to `tests/skills/agentskills-research/fixtures/upstream/`; SHA dirs are created at run time), `skills/agentskills-research/{SKILL.md,README.md}`, `scripts/audit/audit.py`, `tests/audit/test_audit.py`; create (first real run) `skills/skill-judge/references/agentskills/docs-navigation.json.txt` and its `SOURCE.json` entry.

**Interfaces:**
- Consumes: plan 2's `fetch-spec.sh` contract (stdout JSON, publish/rollback, `SOURCE.json`), `audit.py rubric-check`, `load_rubric`.
- `fetch-spec.sh` downloads `docs/docs.json` first and tracks it as an 8th file, `docs-navigation.json.txt` (first line `# Source: https://github.com/agentskills/agentskills (CC-BY-4.0), verbatim copy, see SOURCE.json`, then a blank line). In-scope pages = every navigation page path (pages are strings or nested `{group, pages}` objects, at any depth) equal to `specification` or starting with `skill-creation/`; other pages (`home`, `clients`, `client-implementation/*`) are out of scope and ignored. Stdout gains `"structure_changed":bool,"new_pages":[page paths],"removed_pages":[page paths]`: `new_pages` = in-scope pages with no entry in the source map, `removed_pages` = mapped doc pages (not the validator) absent from the in-scope set. A removed page is not downloaded (no 404 abort); its committed copy is kept until the research skill drops it from the source map, so rubric citations stay readable during the update. `docs.json` failing to download or parse is a fetch failure (exit 1, nothing published).
- `fetch-spec.sh [--pages-dir DIR]`: with the option, the same run downloads every in-scope page of the resolved upstream SHA (mapped or not, so pages newly listed in `docs.json` included; removed pages are not) as raw upstream files to `DIR/<page path>.mdx`, and regenerates `DIR/pages.json` from `docs.json` as `[{"page","raw":"<page path>.mdx","mapped":bool}]` (`mapped` = the page has an entry in the source map). `DIR` is scratch input for the repair job: it is never published into the references, never changes `changed`, and a download failure there is a fetch failure (exit 1). Without the option nothing changes.

- `agentskills-research` `SKILL.md` gains a section "When upstream structure changes", run when `structure_changed` is true or `rubric-check` reports a broken anchor: add or remove the page in `fetch-spec.sh`'s source map (and its test fixtures and tests), add or delete the reference copy, re-map every affected rubric `source`, review the rubric criteria a new page adds or a removed page took away, bump `rubric_version`, keep `skill-judge`'s eval `files` lists in sync with the sources the rubric cites (plan 2 Task 2 Step 6 invariant), and finish with `rubric-check` and `test-fetch-spec.sh` passing. A new page's content comes from the pre-downloaded `--pages-dir` copy (the repair job has no network), which becomes its verbatim reference copy: the standard `<!-- Source: https://github.com/agentskills/agentskills (CC-BY-4.0), verbatim copy, see SOURCE.json -->` header first, then the upstream bytes, plus a `SOURCE.json` `files` entry holding the sha256 of that file including the header (the value `fetch-spec.sh` computes, so the next fetch sees no change). All of it lands in the audit PR: the `rubric` job (Task 3 job 2) captures every change, deletions included, in `repairs.patch`, which later jobs apply and the PR job commits.

### Task 3: Workflows, prompts and runners

**Files:**
- Create: `.github/workflows/skill-audit.yaml`, `.github/workflows/skill-audit-gate.yaml` (the agent-mode merge gate: `pull_request_review`, `pull_request: synchronize`, `check_suite: completed` and `workflow_run` of `CI` triggers, plus a 6-hourly `schedule` sweep if Task 1 Step 3 found that bot reviews do not trigger workflows)
- Create: `.github/audit/{rubric,merge,fix,upstream}-prompt.md`
- Create: `.github/audit/copilot-runner.sh` (eval runner: stdin prompt → `copilot -p "$(</dev/stdin)" -s --no-ask-user --model "$AUDIT_MERGER_MODEL"` with the no-tools flags recorded in `ci-spike.md`; used only by `audit.py run-evals`)
- Create: `.github/audit/copilot-agent.sh` (editing invocation: the same call with the read/write tool flags recorded in `ci-spike.md` Step 2, run from `$GITHUB_WORKSPACE`, no shell tool; used by `rubric`, `merge` and the `apply` fixer, so they can edit or write files in the checkout)
- Modify: `README.md` ("Automated audits": knobs, the Task 1 Step 5 prerequisites, the `audit-upstream` issue and how to approve upstream updates)

The judge prompt is not copied into CI: the `research` legs fill the repo's `skills/skill-judge/references/judge-prompt.md` at run time (plan 2's contract), so there is one source.

Synced skills (`SYNCED`: `gepetto`, `datadog-cli`) are never judged, researched, merged or fixed by the scheduled audit: the daily `sync-*` workflows overwrite them. `judge_skills` = all skills minus `SYNCED`; it is the one list `detect` (its `skills` output), the research legs, `evals`, `merge --skills` and `validate-decision` use. `docs/audit/upstream-findings.md` is written only by plan 4's manual pass; no scheduled step writes it.

Repo variables and secrets are not exported to shell steps; each reaches a job through `env:`. Workflow-level `env` (variables and inputs only): `AUDIT_LAST_STATE: ${{ vars.AUDIT_LAST_STATE }}`, `AUDIT_RESEARCH_MODELS: ${{ vars.AUDIT_RESEARCH_MODELS }}` (comma list; only `detect` reads it, see job 1: workflow `env` is not available to `strategy.matrix`), `AUDIT_MERGER_MODEL: ${{ vars.AUDIT_MERGER_MODEL }}` (the one name for the merger model everywhere, including both wrappers), `AUDIT_PR_DIAGRAMS: ${{ vars.AUDIT_PR_DIAGRAMS }}`, `APPROVED_UPSTREAMS: ${{ inputs.approved_upstreams }}` and `AUDIT_MERGE_MODE: ${{ inputs.merge_mode || vars.AUDIT_MERGE_MODE }}` (the dispatch input overrides the variable for that run only; a scheduled run has no input and uses the variable). Secrets are set per job, never at workflow level: `COPILOT_GITHUB_TOKEN: ${{ secrets.COPILOT_GITHUB_TOKEN }}` in every job that runs `copilot` (`rubric`, `research`, `evals`, `merge`, `apply`, `upstream-report`); `GH_TOKEN: ${{ secrets.AUDIT_BOT_TOKEN }}` (the `AUDIT_BOT_TOKEN` secret) in `apply`, `merge-knob`, `upstream-report` and `state`, and in `skill-audit-gate.yaml`; `detect` uses the default `GITHUB_TOKEN` (its permissions below). Every job that runs `audit.py check` installs `uv` (`astral-sh/setup-uv`).

Permissions: both workflows declare `permissions: {}` at the top level and a `permissions:` block on every job (a job block replaces the workflow default, and any key a block omits is `none`), so the repository's default workflow-token setting is never relied on (verified in Task 1 Step 5, exercised by Step 6). `variables` is not a `GITHUB_TOKEN` permission key (actionlint rejects it): writing `AUDIT_LAST_STATE` is done by `AUDIT_BOT_TOKEN`. Jobs that use only `AUDIT_BOT_TOKEN` and no checkout (`merge-knob`, `state`, the gate) also set `GH_REPO: ${{ github.repository }}` because `gh` has no checkout to infer the repository from.

| Job | `permissions:` |
|---|---|
| `detect` | `contents: read`, `pull-requests: read`, `issues: read` (open-PR label check on the default token) |
| `rubric`, `research`, `evals`, `merge` | `contents: read` |
| `apply` | `contents: write`, `pull-requests: write`, `issues: write` (the push, PR and labels use `AUDIT_BOT_TOKEN`, a PAT, so that their events trigger CI and `auto-bump`; the block bounds the default token) |
| `merge-knob` | `{}` (acts through `AUDIT_BOT_TOKEN`) |
| `upstream-report` | `contents: read`, `issues: write` (issue write through `AUDIT_BOT_TOKEN`) |
| `state` | `{}` (variable write through `AUDIT_BOT_TOKEN`) |
| gate job (`skill-audit-gate.yaml`) | `{}` (reads and merges through `AUDIT_BOT_TOKEN`; no checkout) |

History: every job whose checkout feeds `audit.py upstreams`, `audit.py detect`'s `git log`/`git merge-base` inputs or any other `git log`/`git merge-base` logic uses `actions/checkout` with `fetch-depth: 0`. Only `detect` recomputes them (the other jobs consume its outputs); a job that later does must also fetch full history. Reason: the default shallow clone (`fetch-depth: 1`) makes every skill's last change the checkout commit and has no older shared ancestor, which suppresses genuinely stale sources while the state advances.

Serialization: `skill-audit.yaml` has the workflow-level `concurrency: { group: skill-audit, cancel-in-progress: false }` (valid at workflow level; a constant group, so scheduled runs, dispatches and `--ref` drills all share it). A run in flight is never cancelled; GitHub keeps at most one pending run per group and replaces an older pending run with a newer one, which is harmless because every run re-reads the variables, labels and open PRs fresh. `detect`'s open-PR check, `apply`'s PR creation and `state`'s variable write therefore all happen inside one boundary: two runs can never publish competing PRs or overwrite each other's state.

Due means `elapsed >= N days - 12h` (the 12 hours absorb cron delay and the fact that `checked_at` is stamped when a run finishes, so the cadence is N days and not N plus one); a missing `checked_at`, an empty state and an unparsable state are due; `workflow_dispatch` is always due. A scheduled run is also not due while `state.last_attempt_at` is newer than `3 days - 12h` (the failure backoff below).
- **Outputs.** `detect` emits `full_check=true` only in its final publish step, after every check succeeded. So `run_needed=false` with `full_check=true` means "checked, nothing to do"; with `full_check=false` it means "interval not due" or an early stop (open audit PR) and must never advance `checked_at`.
- **Checkpoint.** Cron becomes `0 6 * * *`. A `checkpoint` job (`contents: read`; a credentialless checkout of the workflow's own ref to obtain `write-state.sh`; `AUDIT_BOT_TOKEN` only in the write step's `env:`) runs only when `!cancelled() && GATE && needs.detect.result == 'success' && needs.detect.outputs.full_check == 'true' && needs.detect.outputs.run_needed == 'false'`. Both read the live `AUDIT_LAST_STATE` variable at write time and merge with `jq` (`.checked_at = now`), and the constant concurrency group serializes them, so the two writers cannot clobber each other.
- **Failure backoff.** A job `attempt` (same shape as `checkpoint`; `needs: detect`; `if: !cancelled() && GATE && needs.detect.result == 'success' && needs.detect.outputs.run_needed == 'true'`) stamps `last_attempt_at` through `write-state.sh`. Every job that starts a model (`rubric`, `research`, `evals`, `upstream-report`) and `merge`, `apply` and `state` get `attempt` in `needs`, and their `if` adds `needs.attempt.result == 'success'`: a failed marker write starts no model and advances no state. A pipeline that keeps failing therefore retries at most every 3 days instead of daily (this matters on the Free quota); a durable outcome stamps `checked_at`.
- **State write contract.** Both writers (`checkpoint` and `state`) run inside the serialized boundary (the constant concurrency group), with `GH_REPO` set, and the `checkpoint` and `state` predicates are mutually exclusive (`checkpoint` only when `run_needed == 'false'`, `state` only when it is `'true'`). Only a 404 (detected as `HTTP 404` in the captured stderr of `gh api`; the stub tests assert the same mechanism) (variable absent) or successfully read invalid JSON starts from `{}` with a notice; any other read failure (authentication, authorization, transport) aborts without writing. **Labels and head binding.** Statuses are authoritative; labels are informational. A push invalidates: the review workflow also triggers on `pull_request_target` `synchronize` (a job `invalidate`, `pull-requests: write`, no checkout, so the default branch's workflow file runs, only for PRs labeled `skill-audit`) and removes every `audit-review:*` label, since the new head has no status. **Outcomes** (`review-combine.py`, a pure function; precedence from the top): `skipped` when `AUDIT_REVIEW_MODEL` is empty (decided in `target`, no gate runs, no status); any gate `fail` yields `changes`, whatever the review says; any gate `needs-human`, absent or malformed (including CI timeout, a missing `skill-audit/evals` status and `diff-size`) yields `needs-human`; then `needs-human` when `review.json` is missing or invalid, the verdict is `unsure` or the reviewer step failed; `changes` when the verdict is `changes` or any finding exists; `positive` only when every gate passes, the verdict is `approve` and there are no findings. ### Design resolutions (answers to the review findings)

1. **Jev access is isolated.** Editing agents (`copilot-agent.sh`, `copilot-runner.sh`) never get a network tool or the jev key. A separate wrapper `copilot-decide.sh` (narrow `--allow-tool`, UNVERIFIED pattern) runs only in decision steps, with the key in step-level `env:` only, in a workspace that holds just the evidence file and the skill. The evidence file is built by a script (`decision-evidence.py`) from a **character whitelist** and an enumerated field list (counts, enums, numeric versions, skill names, validated section slugs); free text from commits, pages or diffs never enters it. `COPILOT_GITHUB_TOKEN` is present in the same step, which is a residual risk; the keys should be dedicated and limited in spend.
2. **jev can only downgrade.** `review-combine.py` ignores any jev answer that lowers a finding's severity or removes a blocker; only "blocking", "not ready" or "unsure" can downgrade a verdict.
3. **P1 per mode.** `AUDIT_MIN_CONFIDENCE` applies **only to jev's confidence**, never to a number the reviewer model reports. With `AUDIT_DECISIONS=agent` or no key, a verdict is positive only if every gate passes, the reviewer verdict is `approve` and there are no findings. `AUDIT_AUTOMERGE` is honored only when a jev answer was recorded for P1 (key present); otherwise automerge is not armed and the PR carries a notice.
4. **Automerge relies on a required check, not on `--match-head-commit`.** Whether `gh pr merge --auto` honors `--match-head-commit` and whether a push disarms it are UNVERIFIED (A3). The safety rests on the commit status `skill-audit/review` on the head SHA being a **required check**: `preflight.sh` fails when `AUDIT_AUTOMERGE=true` and that context is not required. A push produces a new SHA with no status, so the merge is blocked. A ruleset that requires an approving review also blocks the merge; document it. `AUDIT_BOT_TOKEN` needs "Commit statuses: write".
5. **`ignore` is bounded.** `structure_changed`, `rubric_stale` and a failing `rubric-check` always override `ignore`; an ignore expires after two intervals (`ignored.until`). `re_review=no` means: record the new judge, judge no skill this cycle, and do not re-judge existing skills until they change (the merge of an audit PR will not retrigger a full re-judge for that cycle).
6. **Upstream `pr` mode keeps a human in the loop.** `AUDIT_UPSTREAM_ACTION=issue` (default) keeps roadmap Decision 11. With `pr`, rows decided `update` join the same channel as `approved_upstreams` (evidence fetched by the trusted script, targets derived from the rows' skills), and the PR is still reviewed (P1); automerge needs a recorded jev answer.
7. **Model resolution has its own job.** `resolve` (after `detect`, before `research`) outputs `models` (`[{requested, resolved, slug}]`); the matrix and `merge --judges` read it. State gains `judges` (resolved IDs), recorded and annotated in the PR (a knob for forced re-judge on model change is deferred). Two lanes resolving to the same ID collapse to one lane with a notice. The family regex also gates membership; zero matches skip jev and go to the previous version (`state.models_seen`), then `auto`.
8. **Gates run keyless (Phase 2 shape; Phase 1 runs them inside the single `review` job without executing PR code).** A `review-gates` job runs scope check, `check --strict`, script tests and reads the `evals` output `quality_failed`; there is no "previous run" eval baseline. It has neither the Copilot token nor the jev key.

### Phase 2 open issues (from review rounds 1 and 2; resolve before implementing)

1. **Skill install and key isolation (HIGH).** Installed code runs on the runner that later holds secrets, and a changed skill hash only blocks P1 after exposure. Isolate the install from secret-bearing execution, accept a revision or hash before exposing keys, restrict endpoints and redirects, and disable jev when containment is unverified (the keyless path is the fail-safe).
2. **Required check and bypass (HIGH).** A bypass actor defeats the required status, and requiring `skill-audit/review` on `main` blocks every non-audit PR. Needs a non-bypass merge identity (verified by preflight) and a trusted status producer for all affected PRs, or a narrower enforceable ruleset.
3. **Cheap model and research skill (HIGH).** The binding requirement has the cheap model orchestrate the research skill; the draft keeps a script fetching and gives triage only metadata. Wire the cheap, keyless orchestrator to the research skill and the actual change evidence, and convert its interpretation into validated enums for the jev step. Owner sign-off on the deviation is still pending.
4. **`rubric_stale` makes `ignore` impossible (HIGH).** `fetch-spec.sh` updates the source pin whenever content changes, so every ordinary change reports `rubric_stale`. Distinguish a pre-existing incomplete refresh from this run's candidate.
5. **`re_review=no` has no executable path (HIGH).** Define a rubric-only decision/apply route and pending versus committed judge state so an unmerged PR is not the baseline and a deliberately non-rejudged merge does not trigger a full re-judge.
6. **Upstream `pr` mode DAG (HIGH).** `detect` cannot consume a downstream job's output. Add an explicit post-triage planning job and make `merge`, `evals` and `state` use its selected skills and keys (note `merge_verdicts()` treats an empty list as all skills; null-skill registry rows are report-only).
7. **Model roles and data contract (MEDIUM).** Resolve every non-cheap role (merger, reviewer) through the family mechanism; define the `models` object contract for the matrix and `--judges`, finalize effective models after lanes finish, define `models_seen` persistence in `detect()`, and supersede Focus 8 and Task 3 Step 8(a) (a missing model now falls back to `auto`).
8. **Failure table per decision point (MEDIUM)** and **injection into the key-holding step:** charset-validate page paths and other upstream-controlled strings in `decision-evidence.py`; define the fallback when no narrow `--allow-tool` pattern exists (no network tool, jev unavailable).
9. **Triage wiring (MEDIUM):** name the triage output that gates `rubric` and `merge`, run `rubric-check` inside triage, and pin `.audit-skills/` exclusion in the scope-check tests.
10. **Owner sign-off line** for the fetch-script deviation, and **A7-style configuration** for the Phase 2 knobs (`AUDIT_DECISIONS`, `AUDIT_JEV_*`, `AUDIT_CHEAP_MODEL`, `AUDIT_MODEL_FAMILIES`, `AUDIT_UPSTREAM_ACTION`, `AUDIT_MIN_CONFIDENCE`) once the spike answers the open items.
