# Plan 14 — Recover Lost Guidance, Re-verify Sources and Facts, Artifact by Artifact

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every skill, command and agent that existed before October 2026 carries all the guidance it had then, unless a recorded decision dropped or moved it. Every artifact, including those added since, has its sources found and reviewed and its version-sensitive facts (model IDs, CLI flags, API endpoints, prices, product names) verified against current official documentation. Every changed artifact still grades 90 or more under rubric v5, with passing evals.

**Why:** Plans 4 and 8 rewrote most artifacts to satisfy the judge. Against the pre-October baseline (`dbff837f`, 2026-09-30), 40 of the 54 changed artifacts keep under 15% of their original phrasing, and 9 keep 40% or more; at most 18% of any artifact moved to another file. A section-level check of four artifacts found real losses, none of them moved to another artifact: professional-communication lost its meeting templates, async norms and jargon glossary; meme-factory its text-meme genre catalog; marp-slide its progress-bar, two-column, GitHub Pages and VS Code material, plus seven `assets/theme-*.css` files (about 1,067 lines); codex lost the `-m` and reasoning-effort flags its procedure relies on; mui lost `skill-rules-fragment.json` (84 lines). Facts also went stale: codex defaults to `gpt-5.2`, which OpenAI has deprecated, and no registry row points at the docs that would show it. [Plan 13](2026-11-06-13-judge-preservation.md) stops the judge from rewarding loss; this plan repairs what was lost. User rulings R1, R2 and the per-artifact half of R4 ([intent](2026-11-06-13-content-recovery-intent.md)).

**Architecture:** One loop per batch of at most 3 artifacts, the plan 8 shape. For each artifact: inventory what was lost (markdown sections and non-markdown files), confirm and triage it by the three R2 questions, find and review sources, verify facts, restore and update, then evals, judge and close. The queue is computed (Task 1, `recovery queue`). It runs the artifacts with the largest share of absent, partial and contradicted text first, then artifacts with no baseline or no change since it (facts and sources only), then the synced ones (report only). Nothing is pasted back wholesale. Lost guidance returns into `references/` when it is domain-specific, a template users ask for, or a tested example, and into the main file only when the procedure depends on it.

**Tech Stack:** `scripts/audit/audit.py` (new `recovery` subcommand; plan 13's digest helpers; `batches`, `track`, `upstreams`, `check`, `run-evals`, `judge-prompt`, `merge`), `skills/skill-judge` (rubric v5), `skills/skill-updater`, pi referee lanes, a presence judge chosen at run time, web search and fetch for official docs, `build_plugins.py`.

**Spec:** this file, [intent](2026-11-06-13-content-recovery-intent.md) (R1, R2, R4 per artifact, and the standing rulings), Roadmap Global Constraints, plan 8 Global Constraints (batch size, rounds, scope check, closing), plan 13's `docs/audit/fixer-rules.md` (fixer rules and the recovery record format).

**PR layout:** branch per PR `fix/<yy-mm-dd>-content-recovery-<n>`, each with its own review, each stacked on the previous one. `<wt>` everywhere in this plan is the absolute path of the git worktree that has the current PR's branch checked out (`git rev-parse --show-toplevel` run inside it), as in plan 13. PR 1 carries Tasks 1-2 and the first four closed batches; each later PR carries the next four closed batches; the last PR carries the remaining closed batches (one to four: the boundary rule in Task 3 Step 8 decides, and with the measured 21 batches, 18 `full`, 2 `facts-only` and 1 `report-only`, it is one, unless `--append` re-queues change the count) and Task 4. Order at the end: the last batch closes; the last Step 8 boundary's Step 3 form runs and every follow-up it triggers finishes (accepted-drop and rejected-drop follow-up rounds `r<k>`, and each `--append` batch run through Task 3 to `closed`), so no batch is `queued`; then Task 4 is committed on the same branch; then the rest of that Step 8 boundary runs once and opens the last PR. Depends on plan 13 merged (rubric v5, the digest, the record format, registry rows for commands and agents). Plans 9 and 11 are not touched.

## Global Constraints

- **As plan 8** (batch size, one dispatch per artifact, rounds, scope check, closing gates), plus the rules below. Differences for recovery batches:
  - The cap is 3 artifacts, and the 15-finding cap does not apply (a record row is not a finding).
  - The queue lives in `docs/audit/recovery/batches.json`. It is driven with `batches set|waive --out docs/audit/recovery` and closed with `recovery check` (Task 1).
  - `batches requeue` is not used: it would overwrite the recovery brief with a finding brief. An artifact still failing after round 3 goes to the user (waive or stop).
  - Closing also needs `recovery record-check` clean for `full`-mode artifacts (Task 3 Step 7).
- **Scope-check allowlist:** plan 8's, with `docs/audit/batches.json` and `docs/audit/batches/` replaced by everything under `docs/audit/recovery/`. That covers `<name>/sections.json`, `presence.json` and `record.md`, plus `batches.json`, the briefs, and the round directories `batches/<id>/r<round>/`. Also allowed: the root `README.md` (credit lines for commands and agents), `docs/audit/upstream-sources.json`, `docs/audit/upstream-sources.md`, `docs/audit/upstream-findings.md`, and `docs/audit/<date>/updates.md` (where `skill-updater` records its reasoning, `skills/skill-updater/SKILL.md` line 8). When a command or agent of the batch restores into a destination skill (Task 3 Step 6), that skill's own paths as plan 8 lists them for a batch skill (`skills/<dest>/`, `tests/skills/<dest>/`, `docs/audit/evals/<dest>/`) are allowed too. The scope check still fails on `skills/gepetto` and `skills/datadog-cli`.
- **Lanes:** two referee lanes per judging or review round is ideal, and one is enough; a third replaces an unavailable one. Lanes are not blockers (standing ruling 2026-11-04/05, recorded in the intent file). This overrides plan 12's "stop with fewer than two lanes".
- **Implementers:** native sonnet subagents (Claude Code `Agent` tool, `model: "sonnet"`, `effort: "medium"`), one per artifact, with no `pi` lane and no `pi-cmd` command. This replaces plan 8 Task 3 Step 2's `my-coding` dispatch (ruling 2026-11-02). Every fixer prompt includes `docs/audit/fixer-rules.md`.
- **Never delete to raise a score.** A removed rule, step, fact, template, example or file needs a row in the artifact's record (plan 13 format). A writer adds rows and never overwrites another writer's rows.
- **Restore, do not paste.** Restored content is rewritten to the repo's current style and checked like new content: when it changes behavior in a skill or a command, an eval scenario exercises it. Agents are exempt from the eval part: no `agents/evals/` exists and plan 8 closes agents without evals, so restored agent behavior is checked by the Step 7 judgment alone (a restore into a destination skill gets that skill's evals).
- **Facts churn: point, do not pin.** When a fact changes faster than the artifact is reviewed (model IDs, default models, CLI versions, prices), prefer instructions that read the live value (`codex exec --help`, the CLI's model list, the API's catalog) over a hardcoded value. When a value must be written, give its source URL and the date checked.
- **Credits are provenance.** Never remove, shorten or reword a credit line (standing ruling). A newly found origin gets a credit line and a registry row.
- **Shell rules:** no `cd` chains, no heredocs, no multi-statement one-liners. Write scripts with the Write tool and run them with `bash /abs/path.sh`. Commit with `git -C <wt> commit -F <file>`. Pass these rules to every subagent.
- **Remote judges:** the presence judge may send artifact text off the machine only under the user's recorded consent for that backend. The repo is public; secrets never go. jev's `ladder` escalates to a consented remote even with `JEV_BACKEND=laya`, so call a backend directly when the run must stay local.

### Task 1: Recovery tooling

**Files:** `scripts/audit/audit.py` (new `recovery` subcommand; `batches check` skips `report-only` artifacts), `tests/audit/test_audit.py` (`RecoveryTests`, plus one case in `BatchTests`), `docs/audit/recovery/`.

**Interfaces** (all reuse plan 13's `artifact_snapshot`, `digest_units`, `unit_id`, `shingles`, `removed_units` and `removed_files`):

- `audit.py recovery inventory --base REF --artifact NAME [--kind skill|command|agent] [--fate-only]` writes `docs/audit/recovery/<name>/sections.json`, which holds `{base, sections, files, phrase_fate}`, and deletes any `<name>/presence.partial.json` (its verdicts belong to the old sections). Without `--kind`, the kind is the one `list_artifacts` gives `NAME`; a name with no match, or with more than one kind, exits 2. With `--fate-only` it prints only the `phrase_fate` object as JSON to stdout and writes and deletes nothing (Task 4 uses it, so the recorded `sections.json` stays as triage left it).
  - `sections`: one entry per section of the baseline's markdown files: `id` (`s001`, `s002`, ... in file order, then document order), `file`, `heading` (`(preamble)` for text before the first heading), `text`, `chars`, `units` (the `unit_id` of each of its units). Sections under 12 words are skipped. A long section is split at unit boundaries into chunks of at most 1,500 characters; each chunk is its own entry and id.
  - `files`: `removed_files(baseline, current, threshold=1.0)`, so every non-markdown baseline file outside `evals/` that is deleted or lost any line.
  - `phrase_fate`: the baseline's shingles that are kept in the same file, moved to another file of any artifact, or gone (the three shares sum to 100%), plus the share of current shingles that are new.
- `audit.py recovery presence --artifact NAME --runner CMD [--timeout SECONDS]` (default 300 seconds per call) runs `CMD` once per section with no arguments added. After each successful call it adds that section's object (`id`, `verdict`, `substantive` true or false) to `<name>/presence.partial.json`, and it skips every section already there, so a re-run resumes and calls the runner only for the sections still missing. When every section of `sections.json` has an object, it writes them, in section order, to `presence.json` (replacing the previous one) and deletes the partial file. A run that starts with no partial file (the Step 7 re-run, for example) therefore judges every section afresh.
  - Each call's stdin: line 1 `MODE: presence`; line 2 `KEY: <name>/<id>` (the keys `tests/audit/fixtures/stub-runner.sh` reads); a blank line; the state, which is each current text file of the artifact (no evals), as a line `=== <repo-relative path> ===` followed by its contents; then the section under `=== previous section <id>: <heading> ===`; then the question "Is this previous section's guidance in the current files? Answer on one line with two words: present, partial, absent or contradicted; then yes or no for whether the section is substantive (a template, procedure, rule or fact a user would miss)".
  - Parsing: the first non-empty stdout line, split on whitespace, must be exactly two tokens: one of the four verdicts, then `yes` or `no` (case-insensitive). Anything else, a non-zero exit or a timeout is a runner failure for that section: its object is not written, the run goes on with the remaining sections, and at the end it exits 1 naming every failed section, with `presence.json` unchanged and the finished verdicts kept in the partial file.
  - On exit 1 the controller re-runs the same command, on another runner (another lane or backend) when the failures look like quota or an outage, or after waiting; it never stops the plan for it (Lanes constraint).
  - The runner is chosen at run time: a wrapper around a TypeSafe/System One client, or a referee lane through `pi-cmd`, that reads this stdin and prints the answer line. The repo names no vendor.
- `audit.py recovery grep --artifact NAME [--min-share 0.3]` prints JSON to stdout. For each `absent` or `partial` section in `presence.json` it gives `{id, heading, verdict, matches: [{path, share}]}`. `matches` lists every file of another artifact (`skills/<n>/` without `evals/`, `commands/<n>.md`, `agents/<n>.md`) that holds at least `--min-share` of the section's 5-word shingles, sorted by share (highest first), then path. Known limit: a move that was rewritten as well escapes the shingle match, and the controller's reading in Task 3 Step 1 is the fallback.
- `audit.py recovery queue --base REF --out docs/audit/recovery [--max-artifacts 3]` lists every artifact with `list_artifacts` (the `audit.py artifacts` listing) and gives each a `mode`:
  - a name in `SYNCED` is `report-only`;
  - an artifact absent at `REF`, or unchanged since it (`git diff --quiet REF -- <path>`), is `facts-only`;
  - every other artifact is `full` and must have a `<name>/presence.json` holding every section id of its `sections.json` (missing or incomplete: exit 1 naming the artifact, nothing written).

  It writes `docs/audit/recovery/batches.json` in plan 8's queue schema (id, artifacts, brief, status, rounds, requeues, waived). Each artifact entry has plan 8's fields with no verdict behind them, `kind` (from `list_artifacts`), `name`, `percent: null` and `findings` with every severity count at 0 (`batch_counts({})`), plus `mode`. Ids start at 1 within this file, and `docs/audit/batches.json` is never touched. It also writes one brief per batch at `docs/audit/recovery/batches/<id>-<names>.md`. When `docs/audit/recovery/batches.json` already exists, it exits 1 and writes nothing (the queue is built once).

  `audit.py recovery queue --base REF --out docs/audit/recovery --append NAME` instead appends one batch holding only `NAME` to the existing file: id one above the highest, status `queued`, `rounds` 0, `requeues` 0, `waived` empty, the mode computed as above. Its brief also lists the artifact's `purpose-change-pending` rows. Every existing batch stays byte for byte; a missing file exits 1.

  Order key: the share of the artifact's baseline section characters whose verdict is `absent`, `partial` or `contradicted`, highest first, ties by name. The `facts-only` artifacts come after all `full` ones, and the `report-only` ones come last. No batch holds more than 3 artifacts. A brief lists, per artifact: its mode, the paths to `sections.json` and `presence.json`, every non-`present` section (id, heading, verdict, chars), and every `files` entry.
- `audit.py recovery record-check --artifact NAME [--previous REF ...]` parses `docs/audit/recovery/<name>/record.md` (plan 13 format), `presence.json` and `sections.json`. It prints each problem and exits 1 when any of these holds:
  - `presence.json` lacks a section id of `sections.json`;
  - a non-`present` section has no row whose `item` starts with its id;
  - a `files` entry has no `file:<path>` row;
  - a row lacks a decision or a valid reason class, or has an empty reason;
  - a row's (fate, value, decision) combination is not one the format allows.

  Then, for each `--previous REF`, it checks the uncapped `removed_units` and `removed_files` (threshold 0.5) of the artifact at `REF` against the current files (the 40-unit cap applies only to judge prompts):
  - when `REF` is the inventory's `base` (`sections.json`; compared as resolved commits), a removed unit whose id appears in a section's `units` is covered by that section's row, whatever the section's verdict. A `present` section that has removed units and no row is reported once, by section id, not once per unit, so the rows needed number at most one per section. These are reworded units, which at under 15% kept phrasing (Inputs) make up most of the units;
  - a removed unit in no section (text added after the baseline) always needs its own `para:<id>` row;
  - for every other `REF` (the pre-batch `BASE`, a follow-up's `FBASE`), a unit present at `REF` and gone now always needs its own `para:<id>` row, even when a section lists it: no section row covers it, whenever that row was written, so a collateral deletion inside a section that already has a row is still reported;
  - a removed file needs a `file:<path>` row.

  This coverage is a subset of the one plan 13's rubric v5 applies (§ Removals and sources, Removal check): a `para:` digest item is explained by a row whose `item` starts with a section id whose `units` in `sections.json` list it, so every unit `record-check` counts as covered the v5 judge can also count as explained, as long as `sections.json` stays committed beside `record.md`. It runs only for `full`-mode artifacts. `presence` and `record-check` never run for `facts-only` or `report-only` artifacts, which have no inventory.
- `audit.py recovery check --out docs/audit/recovery` runs `batches check --out docs/audit/recovery` with `--merged` set to every existing `batches/<id>/r<round>/merged.json`, ordered by batch id, then round number, both numeric (later files win per artifact). It therefore covers every closed batch, not only the latest one, and needs no shell glob. With no round files, it passes an empty list, so any closed batch with an artifact that needs a verdict fails.
- `batches check` skips artifacts whose entry has `mode: report-only`: they are never judged, and their batch closes on Task 3 Steps 4-5 alone.

### Task 3: Run one batch (repeat until the queue is empty)

Repeat for each batch with status `queued`, lowest id first. Open it with `python3 scripts/audit/audit.py batches set --id <n> --status open --out docs/audit/recovery`, then note `BASE`, the output of `git -C <wt> rev-parse HEAD`. Each artifact runs the steps its `mode` allows:
- `full` runs every step;
- `facts-only` skips Steps 1-3 and runs Step 6 on facts and sources only;
- `report-only` runs Steps 4-5 and skips Steps 6-7.

- [ ] **Step 1: Verify the losses and classify them** (`full`). For every `absent`, `partial` or `contradicted` section and every `files` entry, the controller reads the old content and the current files and confirms or rejects the verdict; `recovery grep` and that reading rule out a move to another artifact. For each confirmed loss, the controller answers the three R2 questions: was it redistributed (where), was it removed only to fit, is it of real value.
- [ ] **Step 2: Triage** (`full`). Add rows to `docs/audit/recovery/<name>/record.md` in the plan 13 format. When the file exists (rows from plan 13's own run, the scheduled audit, or an earlier batch), keep every existing row; add rows only for items that have none, and change an existing row only by the drop or purpose-change rewrites (Step 3).
  - Add one row per non-`present` section (a rejected verdict is `not-lost`) and one `file:` row per `files` entry.
  - Then run `recovery record-check --artifact <name> --previous dbff837f --previous <BASE>`, and add a row for each item it names. A `present` section it names gets one section row after the controller reads the section's removed units against the current files: `not-lost`, `real` or `low` (the section's value), `none`, `text-present` when the guidance is there in new words, or the loss fate and decision Step 1's R2 questions give when reading finds a real loss. A unit in no section, and any unit removed since `<BASE>`, gets a `para:<id>` row and a file a `file:<path>` row. Repeat after each fix round.
  - `contradicted` sections that were deliberate safety fixes are `intended-change`, `safety-fix` (example: codex no longer sends stderr to `/dev/null`).
- [ ] **Step 3: User gate (never blocks a batch).**
  - A `drop` of a substantive section is recorded as `drop-pending`, and Step 6 restores the section to `references/` in the meantime (the safe default), except when the row's reason class is `wrong` or `stale`: that guidance is already judged incorrect (R2 restores only content of real value), so it stays out until the user answers. A section is substantive when its `presence.json` entry has `substantive: true`, or when the controller rates it so on reading it; the controller may raise the presence judge's rating, never lower it. `drop-pending` counts as a decision for Step 7.
  - A change of the artifact's purpose is recorded as `purpose-change-pending` and is not applied. The change is the restore: a lost section of real value whose return would bring back a purpose the baseline served and the current version dropped. The user is asked whether to restore that purpose or keep the current one.
  - At the PR boundary (Step 8), all pending rows of the PR's batches go to the user in one AskUserQuestion form before the push.
  - Accepted drop: the row gets plan 13's accepted-drop rewrite (decision `drop`, reason "user accepted the drop (<date>)", the other fields kept). A follow-up then removes the restored section (nothing to remove for a `wrong` or `stale` section) and re-runs that artifact's Step 7 gates:
