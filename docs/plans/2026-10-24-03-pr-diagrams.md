# Plan 3 — `pr-diagrams` Skill and `explain-pr-changes --diagrams`

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `explain-pr-changes` can render diagrams as Mermaid (inline) or draw.io (PNG on a shared `pr-diagrams` branch), and promotion PRs reuse earlier PR bodies, diagrams and reviewers instead of regenerating them.

**Architecture:** A new skill `pr-diagrams` owns one tested bash script that resolves the target repository from `origin`, talks to the GitHub Contents API (no checkout, no per-PR branch), renders draw.io files in an isolated scratch repo, and normalizes reviewers. The command `explain-pr-changes` gains arguments and a mode decision; its plugin bundles `pr-diagrams` and `draw-io`. The skill is gated by the plan 2 judge and its evals; the command is gated by its own command evals, run through a new `audit.py run-evals --eval-file` mode.

**Tech Stack:** Bash, `gh`, `git`, `jq`, Python 3 stdlib (`scripts/audit/audit.py`), drawio CLI via `skills/draw-io/scripts/convert-drawio-to-png.sh`.

**Spec:** [Roadmap](2026-10-24-00-roadmap.md) — Decisions 2, 12, 15, 16, 19; planner calls C1, C2; Global Constraints apply.

Branch: `feat/<yy-mm-dd>-pr-diagrams`. Depends on plan 2 (judge, `run-evals`).

## Review Focus

1. An agent creates branch `pr-diagrams/<N>` instead of folder `<N>/` on `pr-diagrams` → `ensure` fails loudly and `publish` refuses. Pinned in Task 2.
2. The command re-runs on an existing PR → the head is pushed first, re-publishing the same file updates it (no 422), the open-PR lookup keeps only PRs whose full head repository (`headRepository.name` and `headRepositoryOwner.login`) is origin's (more than one left → stop), the PR is never its own reuse source (open PRs and the current PR are excluded, `--reuse-from` naming the current PR or any PR that is not merged is rejected before any PR write, recency is `merged_at`), a stacked base is never changed, and a re-run authors the same name `pr-<N>` so it overwrites in place (a stale file in the folder is never linked, because reuse reads only PR bodies). Pinned in Tasks 2-3.
3. `--diagrams=mermaid` (the default) or `none` → no `pr-diagrams` branch is created or pushed to, nothing is written to it, and a feature PR needs no `pr-diagrams.sh` and REPO is parsed inline (roadmap C1 as amended: mermaid never creates or writes `pr-diagrams`, the command may push the PR head, and a diagram is authored only when the changes warrant one). The new feature-head push, fetch, base-from-open-PR, detached-HEAD and head == base guard are recorded behavior changes (Task 3 Step 8); a promotion head (`develop`, `staging`, `main` by default) is never pushed, and one that differs from `origin/<head>` stops the command. Pinned in Task 3.
4. A B→C promotion whose range holds earlier promotions into B and PRs merged directly into B → every related merged PR whose `base_ref` is B is a source (two A→B promotions and a hotfix merged into B are all included: one source is copied verbatim, several are consolidated), and the copied source bodies carry over unchanged in `mermaid` and `drawio` modes (nothing on `pr-diagrams` is read or touched). The same holds for Mermaid blocks in those bodies (they count as an existing diagram and are kept in `mermaid` and `drawio` modes; `none` strips diagram links and Mermaid blocks, keeping other images). A new diagram is authored only when warranted and no selected source body already contains a diagram (diagram link or Mermaid block; a screenshot is not a diagram). A reuse title replaces an existing `[x → y] ` prefix instead of stacking it. Pinned in Tasks 2-3.
5. The drawio render fails (CLI missing, export error) or the script is unavailable on a drawio feature PR → nothing is published, the caller's git index is untouched, and the PR still opens with an inline Mermaid fallback and a reported error (a missing script on `--reuse-from` or a promotion head stops the command before any push or PR write, in every diagrams mode; a final body edit failing after a successful publish is reported first and leaves the fallback body). Any failed read (`related`, `reviewers`, `gh pr view`, `git fetch`) → the command stops before any PR write and names the call. PRs always open on `origin`'s repository. A relevant PR beyond the first page of a GitHub listing is still found, or the command stops with a named error. Two inputs with the same basename never share one render. A bot reviewer (real REST `user.type == "Bot"`, such as `copilot-pull-request-reviewer`) never reaches `--add-reviewer` or cancels the human reviewers. An API rate limit (HTTP 403/429) on `related` stops the command with a named "rate limited" error. A consolidated body over 65,000 characters falls back to one linked line per source, and a failing `gh pr create` or `gh pr edit` stops the command with nothing published and the temp directory removed. Pinned in Tasks 2-3.

**Interfaces:**
- Target repository: always origin's. `pr-diagrams.sh repo` prints `<owner>/<repo>`: (tests only) env `PR_DIAGRAMS_REPO` when env `GH` is also set to a stub (any value other than `gh`; otherwise the env var is ignored with a stderr note), else parsed from `git remote get-url origin` (https, `git@github.com:` and `ssh://` forms, optional `.git`). A non-GitHub or unparsable origin URL exits 1 naming the URL. Every other subcommand resolves the repo once this way and calls `gh api repos/<owner>/<repo>/…` with the resolved names (never `{owner}`/`{repo}` placeholders; `gh api` has no `--repo` flag). Git pushes go to the remote `origin`.
- `pr-diagrams.sh ensure` — if `origin` has no `refs/heads/pr-diagrams`, create it as an orphan from the empty tree (`git commit-tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904 -m "pr-diagrams: init"`) and push to it; exit 1 if any `refs/heads/pr-diagrams/*` exists locally or on `origin`.
- `pr-diagrams.sh publish <PR> <file>...` — runs the same per-PR-branch check first (exit 1 naming the rule). Destination: each file is uploaded as `<PR>/<name>` where `<name>` is the basename of the local path (the files may live in any directory, for example an absolute scratch directory). Before any API call, every argument is validated and a failure exits 1 naming it with no GET or PUT: `<PR>` must match `^[0-9]+$`, every file must exist, and every `<name>` must match `^[A-Za-z0-9][A-Za-z0-9._-]*$` (no slash, no leading dot, no spaces). Per file: GET `repos/<owner>/<repo>/contents/<PR>/<name>?ref=pr-diagrams --jq .sha`; only a failure whose stderr contains `(HTTP 404)` means "new file" (`gh api` exits 1 for every HTTP error, so any other GET failure, such as auth or 5xx, exits 1 naming the file and sends no PUT). Then PUT whose JSON body carries `branch: "pr-diagrams"`, `message`, base64 `content`, and `sha` when the GET found one (a PUT without `branch` would write to the default branch). The body is written to a temp JSON file (built with `jq --rawfile`, never from argv) and sent with `gh api --method PUT … --input <file>`, never as `-f content=…`: a single argv string is capped at 128 KiB and a 2x-scale PNG exceeds that once base64-encoded. On any API failure: stderr names the file, exit 1, no stdout. Success stdout `[{"file","path","url"}]`, path = `<PR>/<name>`, url = `https://github.com/<owner>/<repo>/blob/pr-diagrams/<PR>/<name>?raw=true`.
- `pr-diagrams.sh related <base> <head> [--exclude-pr N]` — runs `git fetch origin <base> <head>`, enumerates `origin/<base>..origin/<head>`, and per commit runs `gh api --paginate --jq '.[]' repos/<owner>/<repo>/commits/<sha>/pulls`: `--jq '.[]'` prints one JSON object per line, so several pages concatenate and the script parses the JSON lines (`jq -s`), never stdout as one document. Call volume: one paginated call per commit in the range, no cap (a release range of hundreds of commits costs hundreds of requests against the 5000-per-hour limit). A failure whose stderr contains `(HTTP 403)` or `(HTTP 429)` exits 1 with stderr `rate limited` naming the commit; any other failure exits 1 naming the commit. A failing `git fetch origin <base> <head>` exits 1 with git's stderr and no stdout. Keeps only merged PRs (`merged_at` non-null) other than `N` (open PRs, including the PR being created, are never sources), deduplicated by number. Stdout `[{"pr","title","head_ref","base_ref","merged_at"}]` sorted by `merged_at` descending then PR number descending ("most recent" always means this order); no related PR → `[]`. It never reads the `pr-diagrams` branch.
- `pr-diagrams.sh list <PR>` — a user-facing listing (the command does not call it): stdout `[{"path","url"}]` for every file in the folder, `.png` and `.drawio` alike, `path` = `<PR>/<name>`, `url` = the `publish` form `https://github.com/<owner>/<repo>/blob/pr-diagrams/<PR>/<name>?raw=true`, never the Contents API `download_url`, which carries a temporary token; `[]` when the folder or the `pr-diagrams` branch does not exist (HTTP 404); any other failure exits 1.
- `pr-diagrams.sh reviewers <PR>... [--exclude LOGIN]` — per PR, two REST reads (not `gh pr view`, whose `reviews[].author` has no type field): `gh api --paginate --jq '.[]' repos/<owner>/<repo>/pulls/<PR>/reviews` (each review's `user.login` and `user.type`) and `gh api --jq '.users[]' repos/<owner>/<repo>/pulls/<PR>/requested_reviewers` (`login`, `type`; `teams` ignored). Only entries whose `type` is `User` are kept, so a `Bot` such as `copilot-pull-request-reviewer` and a review whose `user` is null are dropped. Stdout a JSON array of the union of logins, case-insensitively deduplicated, sorted, without `LOGIN`. A failed read exits 1 naming the PR.
- `pr-diagrams.sh render <file.drawio>...` — first, when the default converter is in use (`$DRAWIO_CONVERTER` unset), checks `command -v drawio` and otherwise exits 1 with stderr `drawio CLI not found` (the converter discards drawio's stderr and exits 0 when the CLI is missing, so the cause cannot be read from its output; a stub `$DRAWIO_CONVERTER` skips this check and owns its own failures). Before converting anything, two inputs with the same basename (for example `a/flow.drawio` and `b/flow.drawio`, which would overwrite each other in one scratch directory) exit 1 naming both paths. Then copies the files into a `mktemp -d` directory that is `git init`ed and runs the converter with that directory as its working directory (the real `convert-drawio-to-png.sh` runs `git add` on its outputs in its CWD under `set -e`: from the caller's repo on temp paths it would fail, from the caller's own directory it would stage into the caller's index) and with the converter's stdout redirected to stderr (it prints `Converting…`, `✓ Generated…` and `Staged N file(s)`, which would corrupt the JSON on stdout), and requires for every input a freshly written `<name>.drawio.png` that is non-empty and starts with the PNG signature (the converter prints a failure and still exits 0, so its exit status proves nothing). Only then copies the PNGs next to their sources and prints `[{"drawio","png"}]`; otherwise stderr names the file and the cause and exit 1 with nothing copied. The converter path is `$DRAWIO_CONVERTER` or, by default, `../../draw-io/scripts/convert-drawio-to-png.sh` relative to the script (valid in this checkout and in an installed plugin, which bundles both skills side by side; a copied-in single skill needs `draw-io` beside it or `$DRAWIO_CONVERTER`).
- Env `GH` (default `gh`) substitutes a stub in tests. Real `gh api` prints the HTTP error body to stdout, `gh: <message> (HTTP NNN)` to stderr and exits 1; the script captures every `gh` call's stdout and forwards nothing from a failed call, so its own stdout is only its documented JSON (nothing on failure, `[]` for `list` on 404). The test stub `GH` mirrors real `gh api` on HTTP errors exactly that way. The test stub `DRAWIO_CONVERTER` must behave like the real converter: it writes status lines to stdout and runs `git add` on its outputs in its working directory (failing if that directory is not a git work tree).

  - `FILE` is resolved against `--root` (default as for `--skills`) and itself must resolve inside the root under `commands/evals/` (a `FILE` elsewhere is a harness error, "eval file must be under commands/evals/"); that is what makes the `files/` directory below safe to resolve.

Both are repo-root-relative, must exist, and are checked by the same canonical containment rule as `file_blocks` (no absolute paths, no `..`, must resolve inside the root).
  - Per-eval fields and validation are unchanged (shared with `load_evals` through one extracted `validate_evals(path, data) -> list[dict]`). Each eval's `files` entries resolve only under `<eval file dir>/files/` (`commands/evals/files/`), with the same containment check.
